# ADR-013: Снимки баланса и поэтапная сверка

## Статус

Принято.

## Контекст

Полное сканирование реестра (`ledger_entries`) становится дорогим, когда у счёта накопились тысячи или миллионы проводок.

Сверка должна оставаться надёжной при росте объёма данных (см. [ADR-007](./adr-007-reconciliation.md)).

## Решение

LedgerPay хранит **неизменяемые** снимки баланса в `account_balance_snapshots`.

Сверка использует последний снимок как базовый баланс и применяет только проводки с `id` больше `snapshot.ledger_entry_id` (стратегия `snapshot_incremental` в metadata отчёта). Без снимка сохраняется прежняя логика полного пересчёта (`full_ledger_scan`).

Снимки создаются:

- после обработки транзакций, когда накопилось N проводок с момента последнего снимка (`config('ledgerpay.snapshots.every_ledger_entries')`);
- по расписанию и вручную: `ledger:snapshot-balances`.

UI: GET `/backoffice/balance-snapshots` (cursor pagination).

Сверка по-прежнему: `reconciliation:run`, scheduler hourly; metadata отчёта описывает использованную стратегию.

## Последствия

Плюсы:

- быстрее сверка на длинной истории счёта;
- меньше нагрузки на таблицу реестра;
- сохраняется append-only аудируемость снимков.

Минусы:

- корректность снимка критична (должен создаваться после ledger write в той же транзакции);
- нужна политика жизненного цикла снимков;
- в production может понадобиться hourly/daily snapshot policy и мониторинг отставания.
